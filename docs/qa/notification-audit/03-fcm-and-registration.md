## Admin Web Push (the only push that exists), code-level and partly verified

- Subscription: `POST /api/admin/push/subscribe` requires a platform-admin session (`requirePlatformRequest(request, 'viewer')`); endpoint, `p256dh`, `auth` validated non-empty; upsert on endpoint. `DELETE` by endpoint. No test in the repository calls these routes; **not executed** here (would need an admin session on a server with VAPID keys).
- VAPID keys: env or generated once and stored encrypted (`encryptSecret`) in `platform_settings`. The public key is served to any admin viewer. The private key is never logged (checked the file: only `publicKey` and error messages are logged).
- Send: `sendPlatformAdminPush` respects `notify_push_signup` / `notify_push_incident` toggles unless `force`. Payload is JSON `{title, body, url}`; `urgency: high`, TTL 24 h.
- Receive: `worker/index.ts` (bundled into `/sw.js`) and `public/admin/sw.js` show the notification with `/icons/icon-192.png`, `tag` `khatario-admin`, `renotify`, `vibrate [200,100,200]`, and on click focus a matching window or open `url`. The root `sw.js` is registered for every business user too (`ServiceWorkerRegistration.tsx`), so its push handler is present in every desktop browser session, but no code ever subscribes a business user and no server code sends to one.
- Not exercised on a device in this audit: the admin PWA on Android Chrome. The staging check would need an admin login on a phone; recorded as BLOCKED in Phase 5.

## What would be needed for business-user push (for the final report's manual actions)

1. Firebase project with Android apps for `com.khatario.app` (and `com.khatario.phone` if the Flutter app ships), `google-services.json` committed per app, a service account for `firebase-admin` on the server (secret in `.env.production`, never in the repo).
2. Capacitor: `@capacitor/push-notifications` (and `@capacitor/local-notifications` for foreground display), `POST_NOTIFICATIONS` in the manifest, a monochrome `ic_stat_khatario` small icon, a notification channel created at app start, deep-link handling from `pushNotificationActionPerformed` to `notificationHref`.
3. Server: a `user_push_tokens` table, register/refresh/unregister routes bound to the session, a sender that joins `notifications` rows to tokens per business, invalid-token cleanup on `messaging/registration-token-not-registered`, retries with backoff for 5xx/429, a delivery log.
4. The same for the Flutter app with `firebase_messaging` + `flutter_local_notifications` if that app is the long-term shell.

None of this was built in this audit because it is new architecture, not a fix, and it needs Firebase Console access and a product decision on which Android app ships.
